Kubernetes security separates **authentication** from **authorization**. Authentication establishes who or what is making a request. Authorization decides whether that identity may perform the requested action.

The command examples create a namespace and a service account, define limited permissions, and test whether those permissions work. A **service account** is an identity used by an application or automated process rather than a person.

## Authentication vs. authorization

Users, service accounts, and external identity providers authenticate to the API server. Kubernetes then evaluates the identity against authorization rules such as RBAC. Passing authentication does not automatically grant access.

## RBAC: Roles and RoleBindings

**Role-based access control (RBAC)** grants the minimum permissions needed for a job. A **Role** lists actions, called verbs, and resources within one namespace. A **RoleBinding** attaches that Role to a user, group, or service account. ClusterRole and ClusterRoleBinding provide cluster-wide scope when it is genuinely required.

```mermaid
flowchart LR
  Identity[Developer or service account] --> Binding[RoleBinding]
  Binding --> Role[Role: get/list Pods]
  Role --> API[Kubernetes API authorization]
```

For example, a deployment service account may need to read ConfigMaps and update Deployments, but it should not automatically read every Secret in the cluster.

## Namespaces

Namespaces provide a scope for names and access policies. Teams often separate `dev`, `staging`, and `prod` workloads into namespaces, then apply ResourceQuotas, NetworkPolicies, and RBAC rules per namespace. Namespaces are useful boundaries, but they are not a complete security boundary by themselves.

## Secrets management

Secrets store sensitive values such as tokens, passwords, and certificates for use by Pods. Kubernetes Secrets are base64-encoded objects, not automatically encrypted plaintext protection. Enable encryption at rest, restrict RBAC access, avoid printing values in logs, and consider an external secret manager for high-value credentials.

## ConfigMaps vs. Secrets

| ConfigMap | Secret |
| --- | --- |
| Non-sensitive configuration | Sensitive configuration and credentials |
| Feature flags, URLs, log levels | Passwords, API tokens, certificates |
| Not a security mechanism | Requires encryption and strict access policies |

Both can be mounted as files or exposed as environment variables. Environment variables can leak through process inspection or diagnostic output, so mounted files or a dedicated secret integration may be preferable for sensitive data.

## Example commands

```bash
kubectl create namespace dev
kubectl create serviceaccount deployer -n dev
kubectl create role pod-reader --verb=get,list,watch --resource=pods -n dev
kubectl create rolebinding deployer-read --role=pod-reader --serviceaccount=dev:deployer -n dev
kubectl create secret generic app-secret --from-literal=API_KEY=replace-me -n dev
kubectl auth can-i get pods --as=system:serviceaccount:dev:deployer -n dev
```
